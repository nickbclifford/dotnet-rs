# Delegates and Method Dispatch

This document describes the delegate system, the multicast delegate stepping protocol, and how method dispatch flows from CIL instruction to executed code.

## Overview

Method dispatch in `dotnet-rs` has several interleaved paths that interact in non-obvious ways:

1. **Normal CIL dispatch**: Instruction → handler function → stack manipulation
2. **Intrinsic dispatch**: Method call intercepted → native Rust handler
3. **Virtual dispatch**: Runtime type → vtable lookup → resolved method
4. **Delegate dispatch**: Special interception before normal method resolution
5. **Multicast dispatch**: Sequential invocation of delegate targets through native effects

## Dispatch Flow (`dispatch/mod.rs`)

### `ExecutionEngine::step`

`step` calls `step_inner`, which:

1. Resumes the innermost native activation if it is runnable (`native_runnable` → `resume_native_effect`; see [Native effects](ARCHITECTURE.md#native-effects)).
2. Otherwise checks the exception state. `None`, `ExecutingHandler` and `Filtering` run `step_normal`; `Throwing`, `Searching` and `Unwinding` route to `handle_exception()`.

`step_normal` (kept `#[inline(never)]`: inlining it into the run loop caused store-forwarding stalls) then:

1. Fetches the CIL instruction at the current Instruction Pointer (`IP`).
2. Records the original IP and evaluation stack height (`original_ip` / `original_stack_height`).
3. Emits an instruction trace when tracing is enabled and records it in the `InstructionRingBuffer` (in `dispatch/ring_buffer.rs`), a circular history of the last N executed instructions for crash context.
4. Dispatches through `InstructionRegistry::dispatch`, whose `match` table is generated by `crates/dotnet-vm/build.rs` (`build_support/codegen.rs`); `dotnet-macros` only provides the `#[dotnet_instruction]` attribute.
5. Processes the `StepResult`:
   - `Continue`: Increment IP and continue loop.
   - `Jump(target)`: Branch to the target IP and continue.
   - `Yield`: Return from `step` to yield control (e.g., GC safe point).
   - `Exception`: Restart the loop to trigger `handle_exception()`.
   - `Return`: Invoke `ctx.handle_return()`, pop the frame, and handle cross-frame exception/return state.
   - `FramePushed`, `NativeSuspended`, `MethodThrew` and `Error` pass through unchanged.

The executor's run loop calls `step` in batches of `DISPATCH_BATCH_SIZE` (128) instructions and
polls for safe points between batches.

### `StepResult` Enum

The `StepResult` enum (defined in `crates/dotnet-vm-data`; canonical path: `dotnet_vm_data::StepResult`) dictates how the dispatch loop proceeds after executing an instruction or intrinsic:

- `Continue`: Instruction executed successfully; advance IP to the next instruction.
- `Jump(usize)`: Branch to the specified IP (used by `br`, `brtrue`, `brfalse`, etc.).
- `FramePushed`: A new method call frame has been pushed to the stack. Do not advance the IP (the newly pushed frame's IP starts at 0).
- `NativeSuspended(NativeId)`: A native activation is parked while its managed child call runs; the ID identifies the activation that resumes after the child returns.
- `Return`: The current method has completed. Pop the frame and resume the caller.
- `MethodThrew(ManagedException)`: Used internally when an exception propagates unhandled out of a frame.
- `Exception`: An exception was thrown (either by a CIL instruction or explicitly). The dispatch loop must call `handle_exception`.
- `Yield`: A GC stop was requested or thread suspension is needed. The execution engine pauses and returns to the caller.
- `Error(VmError)`: A host-side VM error occurred (for example, metadata/type resolution failure, invalid CIL, invalid memory access, or P/Invoke load failure). This is distinct from managed .NET exceptions, which flow through `Exception`/`MethodThrew`.

## Delegate System (`dotnet-intrinsics-delegates`)

### How Delegates Work in .NET
A delegate is an object that wraps a method reference (and optionally a target object). `MulticastDelegate` chains multiple delegates together.

### Delegate Object Layout

Delegate objects in `dotnet-rs` mirror the standard .NET `System.Delegate` layout. The fields are support-assembly runtime slots, accessed through the typed `DelegateView` / `DelegateViewMut` helpers (`crates/dotnet-intrinsics-delegates/src/helpers.rs`). Those helpers use the generated support-slot accessors `delegate_target_field`, `delegate_method_index_field` and `multicast_delegate_targets_field`, which look a field up by its validated slot ID and declaring `TypeDescription`, not by name:
- `_target` (ObjectRef): The `this` reference for instance methods. For static methods, this is typically null.
- `_method` (usize): A method index. This index points to a `MethodDescription` cached in the runtime's global lookup.
- `targets` (ObjectRef, on `System.MulticastDelegate`): For multicast delegates, an array of individual delegate objects.

Delegate invocation and intrinsics such as `Delegate.Target` and `Delegate.Method` read and write these fields only through those accessors. See [Support-assembly slot annotation policy](ARCHITECTURE.md#support-assembly-slot-annotation-policy).

### Special Dispatch Path: `try_delegate_dispatch`

Delegate dispatch runs inside `VesContext::dispatch_resolved_method_with_mode`, after method
resolution, and only for body-less methods. That function runs in one of two
`ResolvedMethodDispatchMode`s:
- `InlineCall` (IL `call`/`callvirt`): it first tries `try_start_multicast` (below), then
  `try_delegate_dispatch_inline`, which invokes the target with `delegate_dispatch_method_inline`.
- `VmContext` (other VM-internal dispatch): it calls `try_delegate_dispatch`.

Both classify the method with `cached_delegate_dispatch_kind`, which memoizes
`classify_delegate_dispatch` in the global `delegate_dispatch_cache`
(`DelegateDispatchKind::{Invoke, Constructor, BeginOrEndInvoke, OtherDelegateMethod, NotDelegate}`,
`crates/dotnet-intrinsics-delegates/src/helpers.rs`):
- `Invoke` dispatches a single-target delegate through `invoke_delegate`.
- `Constructor` returns `None`; the support-library stub handles it.
- `BeginOrEndInvoke` throws `System.NotSupportedException`.
- `OtherDelegateMethod` and `NotDelegate` return `None` to fall through to normal dispatch.

### `invoke_delegate`

Single delegate invocation:
1. Pop the invoke arguments into the VM's reusable buffer (`pop_call_args_into_buffer`), then pop the delegate object
2. Read target object and method index through `DelegateView` (centralizing the `_target`/`_method` layout invariant)
3. Resolve the method from the index
4. Push the target when it is bound, repush the arguments in order, and dispatch the resolved method. As in the CLR, binding follows arity (`delegate_target_is_bound`): the target is bound exactly when `Invoke` takes one argument fewer than the target method, counting `this`

### Multicast invocation

`VesContext::try_start_multicast` (`stack/native_effects.rs`) selects the effects path before
consuming the operand window. It returns `None` (fall through to single-target dispatch) unless
the method is an instance `Invoke` with enough operands whose `cached_delegate_dispatch_kind` is
`Invoke`, the receiver is non-null, and its invocation list has more than one entry or a single
entry other than the receiver. It throws `InvalidProgramException` before committing operands
when a byref argument has a `Transient` origin (including typed references) or when the return
or an argument shape is unsupported. Otherwise it starts `multicast_entry` as a native activation.

The body roots the arguments and calls each target through the transparent call effect,
resolving targets on demand. The last return, including an unchanged byref, is published. A
throwing target stops the list (see [Delegates ↔ Exception Handling](#delegates--exception-handling)).
A pending target remains staged across type initialization. Single-target delegates remain
synchronous. Plan [26](plans/26-thread-lifecycle-and-multicast-fallback.md) records the supported
argument shapes.

### Key Delegate Intrinsics

| Intrinsic                 | Purpose                                   |
|---------------------------|-------------------------------------------|
| `delegate_combine`        | Creates multicast from two delegates      |
| `delegate_remove`         | Removes a delegate from a multicast chain |
| `delegate_equals`         | Compares two delegates for equality       |
| `delegate_get_target`     | Returns the target object                 |
| `delegate_get_method`     | Returns the method info                   |
| `delegate_get_hash_code`  | Hash for delegate identity                |

`Delegate.Equals` and `GetHashCode` are registered for both `System.Delegate` and
`System.MulticastDelegate` (`crates/dotnet-intrinsics-delegates/src/operations.rs`).
`DynamicInvoke` is not an intrinsic: the support assembly's `Delegate.cs` walks
`GetInvocationList()` and calls `MethodInfo.Invoke` for each entry, so argument conversion and
`TargetInvocationException` wrapping match reflection invoke. Only `BeginInvoke`/`EndInvoke`
throw `NotSupportedException`.

## Virtual Dispatch

### Virtual Dispatch Algorithm (`callvirt` in `instructions/calls.rs`)

1. **Resolve**: `dispatch_callvirt` resolves the base method with `find_generic_method` (a vararg target throws `InvalidProgramException`).
2. **Peek receiver**: it reads `this` with `peek_stack_at(num_args - 1)`; arguments stay on the stack.
3. **Null Check**: If `this` is a null `ObjectRef`, it drops the arguments and throws `System.NullReferenceException` (a non-reference receiver is a type error).
4. **Type Extraction**: The runtime type of `this` is taken from its heap descriptor, or from the managed pointer's `inner_type` for value types.
5. **Unified Dispatch**: it calls `ctx.unified_dispatch(UnifiedDispatchTarget::Resolved(base_method, lookup), Some(this_type), None)` (or `unified_dispatch_tail` under `tail.`).
6. **Resolution**: `unified_dispatch_common` calls `resolve_virtual_method`, which walks the inheritance chain and interface implementation tables for the most-derived implementation; the result is cached in the VMT cache (the key includes the generic lookup).
7. **Execution**: the resolved method goes to `dispatch_method_inline` (or `dispatch_method_tail`) and on to `dispatch_resolved_method_with_mode`.

*Note on Constrained Calls*: `callvirt` prefixed with `constrained.` uses `callvirt_constrained` to avoid boxing value types if they directly implement the method. It checks for a direct override before falling back to boxing and virtual dispatch.

### Interface Dispatch
- Interface methods are resolved to concrete implementations via interface maps
- The resolver walks the type's interface implementation table

## Intrinsic Dispatch

### Call Interception Path
Every resolved call, from IL or from VM-internal and `ExecutionEngine` API entry points, goes
through `dispatch_resolved_method_with_mode` (`stack/call_ops_impl.rs`), in this order:
1. `classify_intrinsic`; an intrinsic goes to `dispatch_method_intrinsic` with
   `NativeDispatchMode::InlineCall` (IL calls) or `NativeDispatchMode::Other`.
2. P/Invoke methods go to `dotnet_pinvoke::external_call`.
3. Body-less methods: multicast (inline mode only), delegate dispatch,
   `try_dispatch_no_body_abstract_virtual` (a `call` to an abstract slot is resolved like a
   `callvirt`), else a "no body" error.
4. Otherwise `call_frame` pushes a managed frame (`FramePushed`), subject to the managed frame
   limit (`DOTNET_RS_MANAGED_FRAME_LIMIT`, default 65,536; `0`/`off` disables it).

### Special Cases
- `Object.ToString` and `Object.GetType` are registered as intrinsics in `intrinsics/object_ops.rs` (via `#[dotnet_intrinsic]`)
- Some intrinsics have metadata that affects dispatch behavior (e.g., `filter_name`)

## Non-Obvious Connections

### Delegates ↔ Exception Handling
A throwing multicast target stops the list. Exception search crosses the native boundary, running the child's cleanup before the outer handler.

### Delegates ↔ Reflection
`delegate_get_method` returns a `MethodInfo` reflection object, connecting the delegate system to the reflection registry (see [Resolution ↔ Reflection](TYPE_RESOLUTION_AND_CACHING.md#resolution--reflection)).

### Virtual Dispatch ↔ Generics
Virtual dispatch on generic types requires resolving the method with the correct generic instantiation. The virtual dispatch cache key includes the concrete type to handle this.

### Intrinsic Dispatch ↔ Build System
The intrinsic PHF table (generated at build time) and the runtime `IntrinsicRegistry` must agree on key format. Both use `dotnet-macros-core::ParsedSignature` for consistency (see [Build-Time Code Generation](BUILD_TIME_CODE_GENERATION.md)).

### Method Call ↔ Static Initialization
Any method call may trigger static field initialization (`.cctor`) for the declaring type. This is checked during method resolution and can cause recursive initialization or cross-thread waiting (see [Type Resolution and Caching](TYPE_RESOLUTION_AND_CACHING.md)).

## Method Resolution and Pointers

### `MethodSource` and `unified_dispatch`

The `MethodSource` enum (from the `dotnetdll` crate) represents an unresolved method reference, distinguishing between raw user definitions (`UserMethod`) and generic instantiations.

`VesContext::unified_dispatch(target: UnifiedDispatchTarget, this_type: Option<TypeDescription>, ctx: Option<&ResolutionContext>)`
(declared in `stack/ops.rs`, implemented in `stack/call_ops_impl.rs`) resolves ordinary method
calls. `UnifiedDispatchTarget` is `Source(&MethodSource)` or `Resolved(MethodDescription, GenericLookup)`;
`call` passes `Source`, while `callvirt` and `calli` pass `Resolved`. The shared
`unified_dispatch_common`:
1. Resolves a `Source` with `find_generic_method`.
2. Throws `InvalidProgramException` for the vararg calling convention.
3. If `this_type` is provided, merges the receiver's generic arguments into the lookup, performs
   virtual dispatch via `resolve_virtual_method` (an interface method the receiver does not
   implement throws `InvalidCastException`), and rebinds the lookup to the resolved method.
4. Forwards to `dispatch_method_inline` (or `dispatch_method_tail` for `unified_dispatch_tail`),
   which reach `dispatch_resolved_method_with_mode`.

### Delegate Creation (`newobj`)

When `newobj` is called on a delegate type (in `instructions/objects/mod.rs`), the runtime applies a special transformation:
- It detects that the requested type inherits from `System.Delegate` or `System.MulticastDelegate`.
- Instead of executing the empty method body of the CIL delegate constructor, it seamlessly swaps the constructor target to the `.ctor` defined on the `System.Delegate` base class.
- The actual initialization logic resides in a C# support library stub bundled with the VM.

### Method Pointers (`ldftn` / `ldvirtftn`)

Delegates require method pointers. These are generated by CIL instructions (in `instructions/reflection.rs`):
- **`ldftn`**: Finds the exact concrete method via `find_generic_method` and looks up its global runtime index. It pushes this index onto the stack as a native integer (`isize`), which will become the `_method` field of a delegate.
- **`ldvirtftn`**: Pops the target `this` object from the stack (null throws `NullReferenceException` unless the `no.` prefix set `skip_null_check`), extracts its runtime type, and performs virtual dispatch. `rebind_lookup_for_ldftn` adds the receiver's type generics and rebinds to the resolved declaring type. It pushes the runtime index of the *resolved most-derived method* onto the stack.

### Tail Calls (`tail.`)

The `tail.` prefix instruction is defined in the CIL standard to indicate that the current stack frame should be discarded before the next call.

`dotnet-rs` implements a guarded form of tail calls for `call` and `callvirt`:

- The `tail.` flag is carried through decoding and the `call` handler dispatches via `unified_dispatch_tail`.
- `callvirt` has a dedicated `CallVirtualTail` handler that performs the required null check / runtime type extraction and then requests tail dispatch.
- Tail-call frame replacement is only performed when `should_honor_tail_call` allows it: the call is immediately followed by `ret`, the evaluation stack is otherwise empty, the call is not inside an exception region, the current method is not synchronized, and the frame has no deferred-return work (`.cctor`, finalizer, native return or constructor result). If the guard fails, the VM falls back to a normal call.
