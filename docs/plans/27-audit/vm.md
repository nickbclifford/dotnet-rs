# VM test audit

Baseline: `8431c1ab86dae93d0c008a016f8cecf682281370`. Assigned source inspection is complete. No tests, fuzz replay, Miri, or Loom runs were executed by this partition. Findings are based on source inspection; inline and provenance reviews are linked below.

## Discovery and configurations

Reproduce the source-location inventory from the baseline checkout:

```sh
rg -n '#\[test\]|#\[.*test\]|#\[ignore|#\[should_panic|```|loom::model|fuzz_target!' crates/dotnet-vm/src crates/dotnet-vm/tests crates/dotnet-vm/fuzz/fuzz_targets --glob '*.rs'
rg -n '#\[cfg|#\[cfg_attr|mod .*tests|test_utils' crates/dotnet-vm/src crates/dotnet-vm/tests --glob '*.rs'
rg --files crates/dotnet-vm/fuzz -g '!corpus/**' -g '!Cargo.lock'
git ls-files crates/dotnet-vm/fuzz/corpus/fuzz_executor
```

The first query is a discovery list, not a list of reviewed cases; examine surrounding functions, macros and `lib.rs` module gates. Source doctest fences in this crate are ignored examples (`intrinsics/mod.rs`, `threading/mod.rs`); no active compile-fail fence was found by the query. The ordinary VM library tests are gated by Cargo feature configuration and module gates; default enables `multithreading`. `fuzzing` enables `src/fuzzing.rs`; the standalone fuzz workspace builds the target with that feature. Loom integration tests require `cfg(loom)`; workers additionally require `multithreading`, STW runs without default features. Miri selectors and replay wrapper are in `docs/CI.md`, `.github/workflows/ci.yml`, and `docs/FUZZING.md`. Three provenance diagnostics are ignored; two substring timings are manually ignored. Corpus files are inputs, not independent source tests.

## Actionable findings

### VM-2 — fuzz unit cases can execute no requested instruction (high; rewrite)

`run_program` in all 13 listed fuzz tests calls `execute_cil_program_with_loader`, which returns silently if `executor.entrypoint(entrypoint)` fails and discards `executor.run()`'s result. These tests intend to exercise specific operations under Miri (including the documented division-by-zero path), but an entrypoint regression or insufficient mock setup can pass every case before execution; even a first-step error prevents later instructions from being covered. Expose a test-only result and execution/step observation or add explicit per-program checkpoints and expected outcomes; preserve tests for expected host errors and invalid input rather than requiring every fuzz input to succeed. Verify `cargo test -p dotnet-vm --features fuzzing fuzzing` and the relevant Miri command in `docs/FUZZING.md`, including a deliberate setup-failure control and confirmation that each advertised path is reached. This is a source-level vulnerability, not an observed baseline failure.

### VM-3 — corpus names do not establish replayed programs (high; rewrite generators)

`generate_structured_corpus` writes manually specified raw CIL opcode bytes; `generate_corpus::encode_seed_bytes` writes textual `Debug` representations of dotnetdll instructions. The target instead obtains `FuzzProgram` through `Arbitrary` and converts its enum values; it never parses either format as CIL or debug text. Thus `seed_arithmetic_add` does not establish that add is run, and `seed_SingleFile_*` does not reproduce the named fixture body. Generated names and replay loaded/executed counts are not semantic regression oracles. Produce bytes whose decode is explicitly checked against intended `FuzzProgram` values, with supported-instruction translation and explicit handling of unsupported fixture IL, or relabel inputs as opaque mutation seeds and add separate faithful program regressions. Preserve meaningful tracked crash inputs after validating their decoding; avoid overwriting corpus indiscriminately. Verify generators with decode/expected-instruction tests and run the blocking replay command in `docs/FUZZING.md`. No individual corpus decode or replay was run here.

### VM-4 — source spelling used as registration oracle (medium; rewrite)

The three `intrinsics_codegen_guard_tests` check that keys, fully qualified handler-call strings, and a hash-derived filter symbol occur anywhere in generated files. The actual contract is registration and dispatch of these intrinsics, and the nonprimitive overload boundary; independent substring presence does not demonstrate correct key-to-handler/filter association. An unrelated entry containing the string can satisfy the assertion, while a correct generator renaming handlers, changing signature hash scheme or formatting calls fails it. Replace with executable `IntrinsicRegistry::get_metadata` checks built from appropriate method metadata and a handler/guest behavior test, including accepted and rejected overload shapes; retain structural generation assertions only for a separately justified generator contract. Verify `cargo test -p dotnet-vm intrinsics_codegen_guard_tests` and focused replacement tests, plus relevant guest fixture tests. This is an inspection conclusion, not an executed mutation.

### VM-5 — tail-call test accepts incomplete execution (medium; rewrite)

`tail_call_chain_keeps_frame_depth_bounded` relies on `run_tail_chain_and_measure_max_depth`, which returns the observed depth after the step limit even if no `StepResult::Return` occurred. A tail-call execution stuck indefinitely at constant depth passes. The contract is bounded stack use while executing and returning through the chain; the non-tail case is a useful growth control but does not establish completion either. Require explicit top-level return before reporting depth, with exhaustion as failure, retaining both depth assertions. Verify `cargo test -p dotnet-vm tail_call_chain` and a temporary non-returning chain control. Inspection only; no mutation run.

### VM-6 — null-only object-reference round trip (medium; strengthen)

`static_fields_round_trip_object_references` stores and loads only null and compares with null. The intended static object-reference preservation contract includes non-null identity: an implementation that always stores or loads null passes. Keep the null control and add a non-null object reference, checking identity after the production static field path (and, if claiming rooting, after collection). Verify `cargo test -p dotnet-vm static_fields_round_trip_object_references`. Inspection only.

### VM-7 — generation guard asserts source spelling (medium; remove or rewrite)

`arena_lifetime_installation_checks_arena_generation` splits `threading/basic.rs` on exact match-arm text and requires the literal `c.stack.arena_identity`. F1.ArenaGenerationMatch requires installation to reject references from a different arena generation; a safe helper extraction, match refactor or renamed context fails without changing that behavior, while presence of the string does not prove the comparison controls installation. `arena_lifetime_mark_command_rejects_stale_registration` already executes the production command with a live positive control and old/replacement/foreign generation negatives; retain it and review whether it covers the intended destination-generation case before removing the scan. Verify `cargo test -p dotnet-vm arena_lifetime_mark_command_rejects_stale_registration` and the corresponding Miri selector in `docs/CI.md`. Inspection only.

### VM-8 — diagnostic ring accepts stale or reordered events (low; strengthen)

`test_ring_buffer_wrapping` pushes IPs 0 through 14 with the same opcode and checks only ten lines each containing `Add`. The diagnostic contract is to report the recent instruction history in order; a ring that repeats a single entry, emits old IPs, or reverses them passes. Assert IPs 5 through 14 in order and include distinct opcode names and a partly filled case; retain capacity behavior. Verify `cargo test -p dotnet-vm test_ring_buffer_wrapping`. Inspection only.

### VM-9 — timed monitor release test does not prove setup (low; strengthen)

`enter_with_timeout_succeeds_after_lock_released_by_other_thread` depends on `spawn_lock_holder` having acquired the block before signaling, but that helper ignores the returned boolean. If acquisition fails, the waiter can acquire an initially free lock and pass without exercising release/wakeup. Assert the holder acquired, preferably coordinate release explicitly after the waiter begins rather than relying solely on a sleep; retain a bounded progress timeout. Verify `cargo test -p dotnet-vm enter_with_timeout_succeeds_after_lock_released_by_other_thread`. Inspection only.
