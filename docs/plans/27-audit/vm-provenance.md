Every test, helper, macro and branch in `crates/dotnet-vm/src/pointer_provenance_tests.rs` was inspected. ## Discovery and execution

`lib.rs` includes this module under tests. `run_il`/`run_program` build CIL resolutions with a minimal thread-local mock corlib and use real `ExecutionEngine::step`, production dispatch, frame and memory operations through `entrypoint_frame`; they do not exercise CLI/assembly-file loading or the full framework. `run_i32_entrypoint` fails for an error, exception or missing result within 100,000 steps. `run_entrypoint_observed` permits explicit stopping and collection; its consumers assert the required result or observed transition, so reaching the limit alone does not establish success. `run_program_with_collection` checks its IP-based collection point was reached. Direct intrinsic probes enter a real `ves_context` but bypass managed call dispatch and supply the state and generic lookup themselves.

The four `control_batch!` wrappers invoke the listed enabled control functions sequentially, with start/ok markers and propagated panics; they are not independent variants. `scripts/pointer_provenance.sh` owns singleton and batch membership, verifies discovery/membership and uses pinned permissive Tree Borrows with leaks ignored in no-feature and MT configurations. It runs ignored `p12`, `p19`, and `p_wide_store_into_int_local` only as diagnostics, with native permission only for p19. See `docs/CI.md` and the root tools audit for runner-count concerns. Non-`p` tests here are native unit tests unless separately selected; do not infer that every one ran in the blocking pointer Miri lane. `p44_native_substring_gc_resume` delegates to the production-engine control owned by the separate native-substring audit.

## Reviewed coverage and disposition

- **Keep: harness smoke and local/heap exposure** — `p00`, `p01`–`p03`, `p09`–`p11`, `p20`, `p35`–`p38`, `homed_object_local_survives_collection`, `p43`. Literal read/write results distinguish local vs heap and managed vs integer-address paths; p09/p43 add nested capacity pressure, p36 and the homed-object case force collection at a checked point, and p37/p38 test assignment after taking an address. `p35`'s zero-only oracle and p09's growth observation have limits in findings below. `p36` tests one-byte direct static access; `p12` remains an ignored wider static-address diagnostic and does not establish a current UB finding.
- **Keep: localloc arithmetic and access** — `p04`–`p08`, `p17`, `p18`, `p21`–`p23`, `p25`–`p30`, `p_null_through_pointer_local_address`, `unmanaged_stind_ldind_round_trips_localloc_native_int`, `pointer_stobj_writes_native_word`. These distinguish pointer conversion, arithmetic formation from dereference, native-width storage, unsigned ordering and actual loop readback; p26's generated mask combines individually expected comparisons rather than using the VM to compute the expected values. One-past/far-OOB probes only form addresses, not dereference them. p29's zero-size and stack setup are addressed below. The fixed 16-byte alignment, non-resizing frame-owned storage and zero-size backing are documented implementation/lifecycle guarantees in `docs/GC_AND_MEMORY_SAFETY.md`; the actual guest-requested extent remains distinct from host allocation size.
- **Keep: block operations and intrinsic boundaries** — `p13`–`p16`, `p24`, `conv_u8_heap_ldelema_matches_conv_u`, `conv_u8_after_far_oob_managed_add_does_not_panic`, `unsafe_as_pointer_heap_array_element_round_trips_raw_write_read`, `byte_memmove_ignores_leaked_method_generics`. p14/p16 check one destination element and Miri executes the whole operation; these are provenance probes for the specific small paths, not full block-content verification. p24 uses initialized separate offsets, positive/negative/width boundary cases and an actual dereference. Memmove explicitly injects the leaked lookup, checks all four intended bytes and an unchanged tail; it tests the intrinsic's defense, not whether production call dispatch leaks generics.
- **Keep: ownership and exception lifecycle** — `p31`–`p34`, `p39`, `p40`, `p41`. These observe actual frames, retained homes, allocation counts, release at return/tail replacement/unwind/teardown, and both accepted/rejected filter paths, including forced collection while suspended. Fresh/rejected serials and scalar/struct values exercise jmp and constructor cases. The counted `RawBlock` assertions reflect the currently documented eager release before frame recycling and thread-local counter; they are internal lifecycle evidence, not universal allocator conformance. p41's claimed growth observation is limited below.
- **Keep: managed-pointer and typed-reference policy** — `ref_field_layout_requires_byref_like_declaring_type`, `box_of_byref_like_value_throws_invalid_program`, `stale_frame_home_byref_read_is_rejected`, `stale_frame_home_byref_write_is_rejected_after_frame_reuse`, `stale_frame_home_object_writes_are_host_errors`, `out_of_bounds_object_writes_throw_access_violation`, `object_store_and_initialize_use_frame_home`, `byref_home_indirect_native_int_preserves_origin`, `frame_home_byref_resolves_into_caller_frame`, `addressed_byref_local_preserves_origin_through_indirect_access`, `p42`. They assert error class or managed exception and successful controls; synthetic stale-pointer IL tests the VM's host rejection policy rather than claiming valid guest CIL. ECMA-335 II.14.4.2 supplies the byref-like layout/boxing basis; F10.FrameHomeChecked supplies the safety basis for checked live homes. `p42` covers all named/unnamed, local/argument and initialized/uninitialized combinations, then copying and forced-collection heap-root/wrong-type cases.
- **Keep diagnostic classification** — `p12_ldsflda_convu_stind_static`, `p19_ldelem_negative_index`, `p_wide_store_into_int_local`. They are explicitly ignored and not evidence of a successful control. p12 is a suspected host-UB/alignment scenario; p19 reports a historically observed panic but currently conflates failure outcomes (below); p_wide asserts that a neighboring local remains unchanged despite an eight-byte store through a four-byte local, and its current permitted outcome remains unverified. Preserve opt-in isolation and do not silently promote these.

## Findings for 27b

**VP-1 — Rewrite — `p35_ldflda_on_stack_value_type_then_ldind` reads only an initialized zero.** A broken field-address/read path that returns or selects another zero-filled location can still return the expected zero; the documented contract is a readable address of the actual field, not merely a zero result. Initialize the field to a distinctive nonzero value, read through the `ldflda` path, and retain the Miri production execution; add a different adjacent field if needed to distinguish field offset. Do not replace the probe with a test-only layout calculation. Verify native `cargo test -p dotnet-vm --lib --no-default-features pointer_provenance_tests::p35_ldflda_on_stack_value_type_then_ldind -- --exact`, and pinned Miri `bash scripts/pointer_provenance.sh controls --configuration no-features --shard 32` plus MT equivalent. Inspection conclusion; no fault injection.

**VP-2 — Rewrite — `p29_localloc_blocks_survive_growth_and_are_16_byte_aligned` relies on guest behavior outside its claimed allocation extent.** The size-zero case writes and reads a byte despite requesting zero bytes; the host currently allocates a one-byte backing block, but the guest has no requested payload byte. In addition its accumulated Boolean remains on the evaluation stack across later `localloc` instructions, contrary to ECMA-335 III.3.47's otherwise-empty stack requirement. A valid implementation enforcing correct CIL, or changing zero-request representation while retaining all valid allocation behavior, can reject this test. Store the accumulator in a local before each allocation, only form/check the zero-size result without dereferencing it, and retain nonzero block alignment, growth and content checks. Keep host zero-size backing checks in `dotnet-utils::raw_block` where that internal property is explicit. Verify native p29 and `bash scripts/pointer_provenance.sh controls --configuration no-features --shard 26`, plus MT equivalent. No runtime comparison performed.

**VP-3 — Rewrite — `p09_ldloca_convu_survives_callee_stack_growth` and `p41_constructor_receiver_survives_nested_growth` request a large callee max stack but never observe capacity growth.** If the caller already has enough capacity, they can pass without the claimed relocation pressure; preserving addresses across actual evaluation-stack growth is the safety regression. Observe capacity before and during the callee and require an actual increase, as p43 does, while retaining the pointer write/read and p41's collection/receiver-root checks. Verify native named tests and pointer control shards 36 and 41 in both configurations. No fault injection performed.

**VP-4 — Rewrite diagnostic before promotion — `p19_ldelem_negative_index` cannot distinguish its reported host panic from the desired managed bounds exception in its outcome.** `run_il` calls `should_break_after_step`, which panics for *any* `MethodThrew`; the diagnostic runner classifies both that panic and an internal panic as `assertion-or-panic`. A fixed VM throwing `System.IndexOutOfRangeException` therefore still reports failure, and the summary alone does not identify the failure origin. Negative array access must produce the managed bounds exception (ECMA-335 III.4.7), and no host panic. Add the missing `IndexOutOfRangeException` to the mock corlib, observe `MethodThrew` and assert the specific exception, fail separately on host errors/panics, then evaluate promotion after a bounded native diagnostic; preserve current isolation until verified. Verify `bash scripts/pointer_provenance.sh diagnostic --configuration no-features --probe p19_ldelem_negative_index --lane native`, then the corresponding MT lane; inspect full logs rather than interpreting any generic panic as the historical bug.
